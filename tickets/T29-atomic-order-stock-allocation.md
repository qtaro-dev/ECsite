# T29 原子的な注文作成・在庫引当

**状態**：未着手  
**フェーズ**：M5 金額と購入  
**推奨実装順**：28/47（番号順ではなく[実装計画](../docs/implementation-plan.md)第3章の順序）  
**一覧へ戻る**：[implementation-tickets.md](../docs/implementation-tickets.md)

## 目的

同時注文でも在庫超過と二重注文を防ぐ。

## 対応要件ID

| ID | 要件定義書の要件 |
| --- | --- |
| INV-02 | 決済中だけ在庫を一時引当する。決済失敗または引当期限切れ時は販売可能在庫に戻す。利用者が申し込む取り置き機能とは別の内部処理として扱う。 |
| INV-03 | 同時注文でも販売可能在庫を超えて引き当てない。引当期限と再試行時の詳細な状態遷移を定める。 |
| ORD-06 | 注文に配送先、商品金額、消費税、送料、決済・注文状態を記録する。 |
| ORD-08 | 決済方式、注文・在庫の状態遷移、送料の内訳と税額の計算規則を定める。 |
| ORD-10 | 注文後の価格・住所・商品情報の変更が過去の注文表示を変えないよう、注文時点の内容を記録する。 |

要件定義書の「詳細化待ち」および古い確認待ち表記は、後続の利用者承認と詳細設計の確定内容を適用する。

## 対象範囲

- DB注文・在庫引当関数とcheckout key。

## 実装内容

- 商品ID順の行ロック、可用数検証、注文・明細・スナップショット・引当・試行の単一DBトランザクション、30分期限、同一checkout keyの冪等処理。
- 商品ID順行ロック、可用数確認、注文/明細/試行/引当の単一取引、30分期限、スナップショットを実装する。
- T28 `quoteId` は本人所有かつ `expires_at > now()` を確認する。IDの存在や見積時スナップショットだけを最終根拠にせず、注文作成直前に本人のカート・配送先所有権・公開状態・現在価格・在庫・有効送料規則・税を再取得・再計算する。在庫不足は注文全体を原子的に失敗させる。商品、数量、価格、送料、税、総額のいずれかがT28見積から変わった場合は注文を作らず409で差額と再見積の次操作を安全に示し、利用者の再確認後に再試行させる。ブラウザ送信額は採用しない。
- 入出力・DB・権限・画面に変更がある場合は、同じチケット内で対応するOpenAPI、Zod、マイグレーション、RLS、テスト、文書を整合させる。

## 対象外

- Stripe決済結果処理、利用者向け取り置き。
- 他チケットの機能と、正本にない仕様の独断追加。必要なら変更案を報告する。

## 受け入れ条件

- 残数1に同時2注文でも1件だけ引当、失敗時全ロールバック、価格・住所・送料版が注文に固定される。
- 残数1の同時注文で1件のみ成功し、失敗時は全変更を戻す。
- 設計との不整合、秘密・個人情報の露出、権限の迂回がない。外部設定が未完了なら接続確認を完了扱いにしない。

## 必要なテスト

- DB統合の並列注文、デッドロック・ロールバック、冪等再送、スナップショット確認。
- 並列競合、ロールバック、同一キー再送、注文値不変を試す。
- 該当する境界・異常・権限のケースを実行し、既存の関連回帰テストも通す。実行できない場合は理由を記録する。

## 完了条件

- 対象範囲の成果物と受け入れ条件が揃い、指定テストの結果を記録した。
- チケット外の変更、設計上の疑問、外部作業の未完了を隠さず報告した。
- 変更点、設計根拠、テスト結果、残課題をLUNAの完了報告に記載し、レビュー可能な差分になっている。
