# T35 注文系の統合検収

**状態**：未着手  
**フェーズ**：M5 金額と購入  
**推奨実装順**：35/47（番号順ではなく[実装計画](../docs/implementation-plan.md)第3章の順序）  
**一覧へ戻る**：[implementation-tickets.md](../docs/implementation-tickets.md)

## 目的

M5の正常系・異常系を通して確認する。

## 対応要件ID

| ID | 要件定義書の要件 |
| --- | --- |
| QLT-01 | 主要操作、異常系、権限、在庫・金額の整合性について受け入れ条件を作る。 |
| DEM-01 | 在庫切れ、注文処理中の在庫不足、決済成功・失敗、互換性不一致・判定不能を確認できるデータまたはテスト手段を提供する。 |
| ORD-01 | 会員がカート、注文確認、テスト決済、注文完了、注文履歴を利用できる。 |
| INV-01 | 在庫切れと注文処理中の在庫不足を再現できるテスト方法を用意する。 |
| INV-03 | 同時注文でも販売可能在庫を超えて引き当てない。引当期限と再試行時の詳細な状態遷移を定める。 |

要件定義書の「詳細化待ち」および古い確認待ち表記は、後続の利用者承認と詳細設計の確定内容を適用する。

## 対象範囲

- 購入導線の統合テストと検収記録。

## 実装内容

- 商品探索→カート→住所→見積→テスト決済→結果→履歴をデータセットで通し、在庫競合・失敗・期限切れ・互換性警告を再確認。
- 探索→カート→住所→見積→Stripeテスト→結果→履歴、在庫競合・失敗・期限・互換警告を通す。
- 入出力・DB・権限・画面に変更がある場合は、同じチケット内で対応するOpenAPI、Zod、マイグレーション、RLS、テスト、文書を整合させる。

## 対象外

- 新機能追加、テスト失敗の無視。
- 他チケットの機能と、正本にない仕様の独断追加。必要なら変更案を報告する。

## 受け入れ条件

- 金額・在庫・注文・決済の表示とDB状態が一致し、原因と次の操作を表示する。
- 表示額・DB残数・注文/決済状態の一貫性を検収表で示す。
- 設計との不整合、秘密・個人情報の露出、権限の迂回がない。外部設定が未完了なら接続確認を完了扱いにしない。

## 必要なテスト

- Playwright主要導線、DB状態照合、Webhook再送、全関連Vitest/RLS回帰。
- Playwright、DB状態、Webhook再送、関連RLS/Vitest回帰を実行する。
- 該当する境界・異常・権限のケースを実行し、既存の関連回帰テストも通す。実行できない場合は理由を記録する。

## 完了条件

- 対象範囲の成果物と受け入れ条件が揃い、指定テストの結果を記録した。
- チケット外の変更、設計上の疑問、外部作業の未完了を隠さず報告した。
- 変更点、設計根拠、テスト結果、残課題をLUNAの完了報告に記載し、レビュー可能な差分になっている。
