## 1. 設計の前提と範囲

本書は、利用者の指示に従い、上記の要件定義書を正本として基本設計を行う。正本には通常送料の具体額・重量物送料の算定、公開デモでの実住所の扱いと削除方針が未決定と記載されている。本書はこれらを勝手に確定せず、変更可能な設計と確認事項として扱う。

初期版は国内向けのポートフォリオ用ECサイトであり、実販売・実課金・実発送を行わない。商品・在庫・会員・配送先・注文・決済状態はバックエンドで管理する。初期版に取り置き、ゲスト注文、構成の保存・再編集、高度な互換性判定は含めない。

## 2. システム全体構成

| 構成要素 | 役割と責務 |
| --- | --- |
| 利用者のブラウザ | 商品探索、構成選択、カート操作、フォーム入力、結果表示。価格・在庫・権限の最終判定は行わない。 |
| Vercel / Next.js | 公開画面と管理画面の配信、画面描画、認証済み操作の受付、価格・送料の再計算、注文処理の調整、決済・メール・SMSとの連携。 |
| Supabase Auth | メール・パスワード認証、メール確認、パスワード再設定、Google OAuth、セッション管理。 |
| Supabase Postgres | 会員補助情報、商品、カテゴリ別仕様、在庫、カート、配送先、注文、決済記録、設定、監査記録を保存。RLSとデータベース関数でアクセス制御・在庫の原子的更新を行う。 |
| Supabase Storage | 管理者が登録する商品画像を保存。公開商品の画像のみ公開する。 |
| Supabase Cron | 期限切れとなった決済中の在庫引当を定期的に確認し、決済状態を照合して解放する。 |
| Stripeテスト環境 | 実課金のないカード決済成功・失敗の再現。ホスト型の決済画面を利用する設計案。ライブ決済は使わない。 |
| SMTP送信先 | 会員確認・再設定・注文通知の実メール送信。接続先は管理画面から変更でき、秘密情報は保護する。 |
| SMSゲートウェイ | 公開デモは模擬送信。開発・テスト時の実端末検証に向け実送信先を差し替えられる境界を設ける。 |
| GitHub / GitHub Actions | ソース・設計・DB変更の履歴、レビュー、静的検査とテスト。VercelのGit連携からPreviewとProductionへデプロイする。 |

通常の通信経路は「ブラウザ → Vercel → Supabase」である。認証ではSupabase Auth、決済ではVercelからStripeテスト環境を呼び出す。決済通知はStripeからVercelの署名検証済みWebhookへ届く。外部からの通知や画面遷移だけを注文成功の根拠にしない。

Supabaseのサービスロール鍵、決済秘密鍵、SMTP認証情報はブラウザへ渡さない。公開可能なSupabase鍵を使う経路にも、テーブル権限とRLSを設定する。Preview環境は本番の個人情報や決済データを共有しない。

## 3. 具体的な技術スタックと採用理由

| 領域 | 採用案 | 理由 |
| --- | --- | --- |
| Webアプリ | Next.js App Router、React、TypeScript | Vercelで画面とサーバー処理を一体的に運用できる。商品ページはサーバー描画、操作部分はクライアントコンポーネントに分ける。 |
| UI | CSS Modulesと共通デザイントークン | 依存を増やし過ぎず、公開ECとして一貫した見た目とレスポンシブ設計を管理できる。 |
| 入力検証 | Zod | ブラウザとサーバーで入力形式を共有し、サーバーで必ず再検証する。 |
| DBと認証 | Supabase Postgres、Auth、Storage、`@supabase/ssr` | ユーザーセッションをサーバー描画とRoute Handlerで扱え、RLSと整合する。 |
| 決済 | Stripe Checkoutのテスト環境、Stripe SDK | 実課金をせず成功・失敗を再現し、決済画面とWebhookの境界を明示できる。 |
| メール | Supabase Auth Send Email Hook、Vercelのメール送信処理、管理可能なSMTP接続 | 認証メールをSupabase Authのフローに保ちつつ、管理画面で接続先を変更できるようにする。 |
| SMS | 共通SMS送信インターフェースとデモ用送信処理 | 公開デモの模擬SMSと、開発・テスト時の実端末検証を切り替えられる。実送信サービスの選定・有料利用は別途確認する。 |
| 定期処理 | Supabase CronとDB関数 | 決済中の在庫引当を期限切れ時に回収し、DBで一貫した更新を行える。 |
| 品質確認 | Vitest、Playwright、GitHub Actions | 互換性・送料・在庫のロジック、購入導線、権限を自動検証する。 |

採用案は技術上の基本設計であり、Stripe、SMTP、SMS等の外部アカウント作成や有料契約を実施したことを意味しない。外部サービスの有料利用が必要になった時点で利用者に確認する。

## 4. フロントエンドとサーバー処理の責務

| 処理 | ブラウザ側 | Vercel側 / Supabase側 |
| --- | --- | --- |
| 商品探索 | 条件の入力、一覧・詳細の表示 | 検索条件の検証、公開商品の取得、必要な情報のみ返却 |
| 互換性 | 選択状態と警告表示、適合商品への移動 | 共通判定ルールに基づく判定と理由の生成。注文確認時にも再評価 |
| カート | 数量編集と概算表示 | カート保存、現在価格・在庫・販売状態の再確認 |
| 送料 | 概算・正式金額の区別を表示 | 発送元、配送先、商品重量・サイズ、管理設定から正式額を計算 |
| 注文・決済 | 配送先選択、注文確認、テスト決済画面への移動 | 最終金額の確定、在庫の一時引当、決済セッション作成、Webhook受信、注文状態更新 |
| 管理 | 入力・一覧・編集のUI | 管理者権限の確認、変更の検証・保存、監査記録 |

商品・仕様の読み取りはサーバーコンポーネントを基本とする。検索条件や構成選択など即時反応が必要な部分はクライアントコンポーネントとする。注文、在庫、決済、管理設定はRoute Handlerまたはサーバー側処理を通す。サーバーコンポーネントから自サイトのAPIを余分に経由せず、データ取得層へ直接アクセスする。

## 5. 認証・認可と権限

Supabase Authを認証の基盤とし、メール・パスワード登録にはメール確認を必須とする。GoogleログインはSupabase AuthのOAuth連携を使い、ログイン・識別に必要な最小限のスコープに限定する。配送先は本サイトで入力する。メール・パスワードによる新規登録と再設定には6桁SMSコードの照合を追加し、通常ログインとGoogleログインには追加しない。

公開デモのSMSは、コード発行・入力・照合まで動作する模擬送信である。実際の電話番号をSMS送信目的で収集しない。この模擬コードは本物の電話番号の所有を証明しないことを、デモ画面に明示する。認証省略機能はDevelopment/Testだけで有効にでき、Vercel Productionでは設定ミスを含めて有効化できないようにする。公開デモの模擬SMSは認証省略とは別扱いにする。

| 役割 | 閲覧・操作できるもの | 禁止されるもの |
| --- | --- | --- |
| 未ログイン利用者 | 公開商品、カテゴリ、商品画像、構成確認、カート | 配送先、注文履歴、管理画面、注文確定 |
| 会員 | 自分のプロフィール、配送先、カート、注文、注文履歴 | 他会員の情報、商品・在庫・管理設定の変更 |
| 管理者 | 商品・仕様・在庫・送料設定・SMTP設定、注文・決済状態の確認 | 権限外データの一括取得、秘密情報の平文表示、公開画面からの管理権限付与 |

画面とAPIの両方で本人確認・役割確認を行う。データベースではRLSを有効にし、公開商品だけを未ログインで閲覧可能にする。会員の配送先・カート・注文は本人IDに限定する。管理者権限は一般会員が自身で設定できない独立した管理データで付与し、サーバーで検証する。サービスロール鍵は信頼できるサーバー処理だけに使い、通常の会員処理では可能な限り本人コンテキストとRLSを使う。

## 6. 画面一覧と画面遷移

| 区分 | 主な画面 / 例示URL | 主な操作 |
| --- | --- | --- |
| 公開EC | トップ `/`、カテゴリ `/categories/[slug]`、検索 `/search` | 用途別導線、検索、絞り込み、並べ替え |
| 公開EC | 商品詳細 `/products/[slug]`、構成確認 `/build` | 仕様の理解、互換性確認、適合商品の探索、カート追加 |
| 購入 | カート `/cart`、配送先 `/checkout/address`、注文確認 `/checkout/review` | 数量変更、概算送料、正式送料・警告の確認 |
| 購入 | 決済遷移、結果 `/checkout/result`、注文詳細 `/account/orders/[id]` | テスト決済、成功・失敗の確認、履歴参照 |
| 認証 | 登録 `/register`、確認 `/verify`、ログイン `/login`、再設定 `/reset-password` | メール確認、模擬SMS、Googleログイン、再設定 |
| 会員 | マイページ `/account`、配送先 `/account/addresses`、注文履歴 `/account/orders` | 配送先の登録・編集、履歴確認 |
| 管理 | ダッシュボード `/admin`、商品一覧・編集 `/admin/products`、在庫 `/admin/inventory` | 商品・仕様・価格・在庫の管理 |
| 管理 | 注文 `/admin/orders`、送料・発送元 `/admin/settings/shipping`、メール `/admin/settings/email` | 注文状態確認、発送元・送料・SMTP設定 |

代表的な遷移は「用途・カテゴリ → 商品詳細 → 構成確認またはカート → ログイン → 配送先 → 注文確認 → Stripeテスト決済 → 結果 → 注文履歴」とする。Googleログイン後も会員画面に戻し、購入に必要な配送先がなければ入力を案内する。互換性不一致は構成確認で詳細、注文確認で短い警告を表示し、注文を妨げない。管理画面はEC画面とナビゲーションを分ける。

## 7. 主要機能の構成

| 機能 | 責務 |
| --- | --- |
| 商品カタログ | 8カテゴリ、用途タグ、公開状態、検索条件、商品画像、カテゴリ別の仕様を管理する。少量の初期データではDB検索と構造化フィルタを使い、外部検索サービスは導入しない。 |
| 互換性判定 | Socket、DDR、フォームファクター、GPU長、CPUクーラー対応Socketを照合し、一致・不一致・判定不能と理由を返す。推薦導線は適合条件を持つ商品一覧へつなぐ。 |
| カート | 未ログインでも操作でき、ログイン時に会員カートと統合する。カート表示は概算で、購入開始時に価格と在庫を再確認する。 |
| 送料計算 | 通常送料、税込商品代金1万円以上の通常送料無料、20kg以上の重量物加算、離島加算なし、管理設定の発送元を扱う。具体額・加算式は未確定。 |
| 注文 | 配送先と金額のスナップショットを保存し、二重注文を防ぎ、決済状態と整合させる。 |
| 在庫 | 実在庫、決済中の引当、販売可能数を区別する。同時注文ではDB内で原子的に引当し、期限切れと失敗時に戻す。 |
| 決済 | Stripe Checkoutテスト環境に注文金額を渡し、署名付きWebhookを照合して成功・失敗を更新する。画面の戻りURLだけで成功扱いにしない。 |
| 通知 | 認証メールと注文関連メールをSMTP送信。SMSは公開デモ用と実端末検証用の送信処理を分ける。 |
| 管理 | 管理者のみが商品、仕様、画像、価格、在庫、発送元、SMTP設定を編集し、変更履歴を残す。 |

## 8. 主要データモデル

| エンティティ | 主な情報と関係 |
| --- | --- |
| `auth.users` / `profiles` / `admin_memberships` | AuthのユーザーIDを基準にプロフィールと管理者権限を結ぶ。管理者権限は本人編集不可。 |
| `addresses` | 会員に従属する複数の国内配送先。注文時には住所を注文へ複製する。 |
| `categories` / `products` / `product_specs` / `product_images` | 商品は1カテゴリに属し、共通情報、カテゴリ別の型付き仕様、画像を持つ。互換性に必要な値は自由文だけで管理しない。 |
| `inventory` / `stock_allocations` | 商品単位の実在庫と、決済中に引き当てた数量・期限・状態。販売可能数は実在庫から有効引当を差し引く。 |
| `carts` / `cart_items` | 会員IDまたは匿名セッションに属するカートと商品・数量。価格は注文時に再取得する。 |
| `orders` / `order_items` | 会員、住所・商品名・単価・税率・送料内訳の注文時点の記録。後日の商品・住所変更から独立させる。 |
| `payment_attempts` / `payment_events` | 注文に対するテスト決済の試行、外部ID、状態、WebhookイベントID。重複イベントを抑止する。 |
| `sms_challenges` | 目的、期限、試行回数、照合済み状態。コードそのものは平文保存しない。 |
| `shipping_settings` / `smtp_settings` / `audit_logs` | 発送元・送料規則、SMTPの公開してよい設定値と秘密参照、管理操作の記録。SMTP秘密は保護領域に置く。 |

主要な関係は「会員 1対多 配送先・注文」「カテゴリ 1対多 商品」「商品 1対1 仕様・在庫」「カート／注文 1対多 明細」「注文 1対多 決済試行」「決済中の注文 1対多 在庫引当」である。構成保存は初期版では永続化しないが、将来 `saved_builds` と構成明細を追加できるよう、互換性判定を特定画面に閉じ込めない。

## 9. 主要状態遷移と整合性

| 対象 | 状態と主な遷移 |
| --- | --- |
| 商品 | 下書き → 公開 → 非公開。非公開の商品は新規購入不可。過去の注文明細は残す。 |
| カート | 編集中 → 注文へ進む → 注文完了後に対象明細を整理。失敗時は再操作できる。 |
| 注文 | 決済待ち → 決済完了、または決済失敗・期限切れ。画面上の「注文完了」は決済完了後だけ表示する。 |
| 決済試行 | 作成 → 処理中 → 成功／失敗／期限切れ。再試行は新たな試行として記録し、同じ注文の二重成功を防ぐ。 |
| 在庫引当 | 引当中 → 決済成功で消費、失敗・期限切れで解放。期限切れの解放前に外部決済状態を照合する。 |

購入開始時、Vercelは商品価格・在庫・送料を再計算し、SupabaseのDB関数で注文と在庫引当を原子的に作る。Stripe側の決済セッション作成には重複防止キーを使う。Webhookは署名・外部ID・イベントIDを検証し、既処理イベントを再適用しない。定期処理は期限切れ引当を照合して解放する。遅延した決済成功、複数回のWebhook、通信失敗時の復旧手順は詳細設計で確定する。

## 10. 外部サービス境界と保護方針

| 境界 | 基本方針 |
| --- | --- |
| Google → Supabase Auth | OAuthの認可コードフローを用い、必要最小限のスコープを設定する。Googleのアクセストークンを商品・注文DBに保存しない。 |
| Supabase Auth → メール | Send Email Hookから署名済み通知をVercelの送信処理へ渡す。管理者が設定したSMTP接続を使い、送信失敗は監査可能にする。 |
| Vercel → SMS | 公開デモでは模擬通知。開発・テスト時だけ所有端末に実送信を試す。実送信サービスの選択・費用は別途承認を得る。 |
| Vercel ↔ Stripe | テスト鍵のみを使い、カード番号を本サイトに保存しない。決済Webhookの署名と再送を検証する。 |
| Vercel → ヤマト運輸情報 | 初期版は公式料金ページへのリンクと、公式情報を参考に登録した送料規則を使う。ライブ料金API連携や実配送は行わない。 |

公開デモでは実販売・実課金・実発送がないことを各購入導線で伝える。会員・配送先・注文へのアクセスは本人と許可された管理者だけに限定する。秘密鍵・SMTP認証情報はVercelの環境別秘密設定またはSupabaseの保護領域に保存し、管理画面に平文を再表示しない。管理設定の更新には管理者権限・監査記録・入力検証を必須にする。決済額、送料、在庫、権限はサーバーが確定し、ブラウザ送信値をそのまま信用しない。

## 11. UIとアクセシビリティの基本方針

ヘッダーにサイト名、検索、カテゴリ、構成確認、カート、会員操作を置く。トップでは用途別導線と8カテゴリを明快に示し、PCパーツの画像・型番・主要仕様によって専門店であることを伝える。色・装飾は控えめにし、価格、在庫、互換性の状態、次の操作を優先して見せる。

デスクトップでは絞り込みを一覧横に置き、スマートフォンでは開閉できるパネルにする。商品カードと詳細で仕様名を統一する。初心者には用語説明と「選ぶときに見る項目」を示し、経験者はメーカー・規格・価格・性能で直接絞り込めるようにする。互換性不一致は理由と適合候補のリンクを表示し、判定不能は別の表現にする。確認を繰り返すモーダルは使わない。

各画面はスマートフォンとデスクトップに対応し、キーボード操作、読みやすい文字とコントラスト、明確なラベル、入力エラーの説明、フォーカス表示を備える。状態は色だけで伝えない。カートでは送料を「概算」、注文確認では「確定」と明示する。管理画面は一覧・検索・編集・保存結果が分かる業務向け構成とし、一般EC画面と混同しない。

## 12. テスト、CI/CD、公開環境

GitHubの変更提案時に、コード形式・型・単体テスト・DB権限テストを実行する。互換性判定、税・送料、同時注文時の在庫引当、注文状態、RLSの許可・拒否を重点的に検証する。Playwrightで商品探索からテスト決済、決済失敗、会員・管理者の導線を確認する。外部サービスは単体テストでは模擬し、接続試験では専用のテスト環境を使う。

GitHubのプルリクエストにはVercel Previewを作り、レビュー後の主ブランチへの反映でProductionへデプロイする。Preview用Supabaseプロジェクト・Stripeテストデータ・SMTP送信先を本番デモと分離する。DBスキーマ変更は版管理し、適用順序と復旧方法をレビューしてから公開する。公開デモでは実課金用の鍵を配置しない。デモデータは管理者以外の操作で管理情報を変更できないようにする。

## 13. 確認事項と詳細設計への引き継ぎ

### 利用者の判断を待つ事項

1. 通常送料の具体額、20kg以上の重量物の加算方法、複数梱包やヤマト運輸の取扱上限を超える商品の料金・購入可否。金銭に関わるため、基本設計では設定可能な計算器までを定め、金額を確定しない。
2. 公開デモで実住所の入力を許可するか、配送先・注文履歴・アカウント情報をいつどのように削除するか。個人情報に関わるため、保存期間を確定しない。
3. 外部サービスの有料契約が必要になる場合の費用上限と承認。Stripeテスト環境、SMTP送信先、実SMS送信先、Vercel・Supabaseのプランは、利用開始前に確認する。

### 詳細設計で決める事項

- 画面ごとの入力・エラー・空状態、詳細な遷移図とUI部品。
- テーブル定義、制約、インデックス、RLSポリシー、監査対象、データ移行・初期商品データ。
- 在庫引当の期限、外部決済の遅延・重複・失敗時の復旧、状態遷移の全条件。
- 送料計算の具体式、税額端数処理、注文時点のスナップショット項目。
- SMTP設定の更新権限と秘密保管、模擬SMSの見せ方、通知文面、送信制限。
- 公開デモの利用規約・個人情報案内、保持期間、アカウント削除・データ消去手順。
- レスポンシブの画面幅、アクセシビリティの検証基準、性能目標、監視・障害時の対応。
